# Engine archaeology

DOOM's engine is full of frozen data: `finesine`, `COLORMAP`, `rndtable`, the
gamma curves, dozens of tuning constants. id never documented the tools that
generated them, and most retellings repeat them without asking where they came
from. This document records, for every hardcoded data blob in `engine/core`,
what it is: a recipe that can be regenerated, a form provably equivalent to a
simpler one, irreducible human tuning, or declarative art and design data.

**Reproducers.** Every derived figure here has a program in `tools/archaeology/`
that recomputes it (the list is in
[tools/archaeology/README.md](../tools/archaeology/README.md)). The
`archaeology` leg runs them all:

```
node tools/archaeology/run.mjs
```

Each reproducer must exit 0 and print the values listed in `run.mjs`'s `expect`
table. Those values are keyed by `ea-NNN` ids, and the same ids label the
figures below, so a failing id points at its paragraph. The four COLORMAP and
WAD reproducers need `wads/lib/` (doom.wad, plus doom2, plutonia, tnt, chex
and hacx for the cross-palette check); without it they are skipped. `run.mjs`
reads no documents: when a figure moves, the prose here is updated by hand.

**What stays true at runtime.** The trig tables are computed at boot and refuse
to run if they differ from the 1993 originals (§1). The whole engine is checked
per tic, gamestate and framebuffer, against goldens for the 13 IWAD demos
(44,580 tics, `tools/golden/`), and `node tools/demo-test.mjs --cross <binary>`
compares the same per-tic fingerprint against an instrumented Chocolate Doom
built by `tools/build-choco-reference.sh`.

## 1. Trigonometry tables — CRACKED, regenerated at boot

`finesine` (10,240 entries, one and a quarter turns, so `finecosine` is
`&finesine[FINEANGLES/4]`), `finetangent` (4,096) and `tantoangle` (2,049)
shipped as 64 KB of frozen data. webdoom computes them at boot instead:
`T_GenerateTables` (`engine/core/tables.c`) is the first call in `D_DoomMain`.

**The recipe:**

- `finesine[i] = (fixed_t)(sin((i + 0.5) · 2π / 8192) · 65536)`
- `finetangent[i] = (fixed_t)(tan((i − 2048 + 0.5) · 2π / 8192) · 65536)`
- `tantoangle[i] = (angle_t)(atan(i / 2048) / 2π · 2^32)`

The cast truncates toward zero, and the sine and tangent sample the middle of
each fine-angle bin (the `+ 0.5` phase).

**The "errors" are canon.** 5,377 of the 10,240 `finesine` entries differ from
an ideal round-to-nearest table by ±1 (ea-001). That is not sloppiness: id
truncated, and every demo ever recorded depends on every one of those bits.
Round correctly and demos desync.

**What a modern libm leaves over.** Against today's libm, the truncation recipe
reproduces `finesine` except for **33 entries** (ea-002): razor-edge values
where the 1992 machine's last bit fell the other way. `finetangent` needs
full-value escapes for 98 entries near the asymptote. `tantoangle` is the
loosest fit: 1,603 of its 2,049 entries are off by more than one unit and
carry a full-value escape, so `atan(i/2048)` is the right shape but not id's
exact computation.

**How the canon is restored.** `engine/core/tables_fix.h`, generated by
`tools/gen-tables.mjs` against `tools/golden/tables-canon.json`, holds a packed
2-bit-per-entry delta stream (0, +1, −1, or escape) for all three tables plus
the escape lists, about 11 KB in all. `T_ApplyFix` replays it, then an FNV-1a
checksum over all 16,385 entries (ea-003) must equal `TABLES_CRC`. A toolchain
whose libm computes differently fails loudly at boot with
`T_GenerateTables: tables differ from 1993 canon` instead of desyncing
quietly; rerun `node tools/gen-tables.mjs` (it needs `build/doom.js`) to
regenerate the stream. Every build (wasm, native, freestanding, cross) runs the
same check.

Reproducer: `tools/archaeology/finesine-stats.mjs`.

## 2. FixedDiv float-vs-integer equivalence — PROVEN

linuxdoom-1.10 computes `FixedDiv` in `double`:
`(double)a / (double)b * 65536`. DOS DOOM used a 64/32 integer `idiv`. Modern
ports use `((int64)a << 16) / b` and trust the demos. webdoom uses the integer
form (`engine/core/m_fixed.h`), and this section is why that is safe.

**Theorem: all three are bit-identical over the guarded domain**
(`|a| >> 14 < |b|`; otherwise the function clamps to `MININT`/`MAXINT`).

The intuition: the guard bounds `|a/b| < 2^14`, so every boundary `k/2^16` the
result could fall on is exactly representable in a double. Round-to-nearest
then cannot carry a quotient across one.

**Proof.** Let q = a/b (exact real). The two paths compute:

- *Double path*: `trunc(rn(q) · 2^16)`. The `·2^16` is exact (a power of two;
  `|rn(q)| < 2^14`, so the product is below 2^30, within the 53-bit mantissa).
- *Int path*: `trunc(q · 2^16)` = `((int64)a << 16) / b`.

They differ only if rounding q to rn(q) crosses a boundary `k/2^16`, or lands
exactly on one (double gives k, integer gives k−1). Two cases:

**Case 1, exact representation** (`a·2^16 = k·b`): q = k/2^16 exactly. Since
`|k| < 2^30 < 2^53`, k/2^16 is representable, so rn(q) = q and both paths
yield k.

**Case 2, off a boundary** (`a·2^16 ≠ k·b`): the distance from q to the nearest
boundary satisfies

```
|q − k/2^16| = |a·2^16 − k·b| / (|b|·2^16) ≥ 1/(|b|·2^16)
```

because the numerator is a nonzero integer. For rounding to reach that
boundary, the half-ULP must be at least as large:

```
½·ulp(q) ≤ |q|·2^{−53}    [normal-number bound; q is never subnormal:
                             |q| ≥ 1/INT32_MAX ≫ 2^{−1022}]
```

That requires `1/(|b|·2^16) ≤ (|a|/|b|)·2^{−53}`, i.e. **|a| ≥ 2^37**
(ea-004 = 137,438,953,472). But `|a| ≤ INT32_MAX < 2^31`. Contradiction.

*Negative operands*: C99 `/` and the `(int)` cast both truncate toward zero, so
both paths agree on sign.

*b = 0*: `(abs(a) >> 14) >= abs(0) = 0` is always true, so the guard fires and
the double path's divide-by-zero is unreachable.

*a = INT_MIN*: `abs(INT_MIN)` is undefined behaviour in C. The guard can miss
for small |b|, and then both paths overflow int32, so both are UB. As a fixed
point value INT_MIN is −32,768 map units, which no DOOM map reaches. The claim
is proven for all int32 except a = INT_MIN.

**Consequence**: the int64 form is correct by proof, not by sampling, and it is
by construction the value the DOS executable produced. As corroboration the
reproducer checks **8,388,608** pairs at the guard edge, the only region where
a mismatch could occur (ea-005), and finds **0** mismatches (ea-006).

Reproducer: `tools/archaeology/fixeddiv-proof.c`.

## 2a. FixedMul — PROVEN

`(fixed_t)(((long long)a * (long long)b) >> FRACBITS)` (`m_fixed.h`), with
`FRACBITS = 16` and `fixed_t` = int32.

**Product bound.** `|a| ≤ INT32_MAX < 2^31`, so `|a·b| ≤ 2^62 < INT64_MAX`
(ea-042 = 4,611,686,018,427,387,904 = 2^62). The int64 intermediate never
overflows.

**Two load-bearing implementation-defined behaviours (IDBs):**

- *IDB-A*: `>> FRACBITS` on a negative int64 (C99 §6.5.7p5).
- *IDB-B*: the int64 → int32 narrowing in the `(fixed_t)` cast when the shifted
  result is out of range (C99 §6.3.1.3p3).

C23 makes two's complement the only representation but leaves both operations
implementation-defined; C++20 defines both (arithmetic shift, modular wrap).
GCC and Clang document sign-extending right shifts and modulo-2^N conversion,
and the engine relies on exactly that. Both behaviours are intended: FixedMul
overflows by design, and the wraparound is demo-visible in trick-shot angles
and movement extremes. "Fixing" either would break demo replay.

**Rounding asymmetry.** FixedMul's arithmetic right shift floors toward −∞;
FixedDiv's integer division truncates toward 0. For a negative product that is
not an exact multiple of 2^16 the two roundings differ by exactly 1 (ea-043);
positive products round the same way. Example: `a = −1, b = 3` gives product
−3; `floor(−3/65536) = −1`, `trunc(−3/65536) = 0`.

*Residual:* `abs(INT_MIN)` is UB, as in §2; INT_MIN is unreachable as a map
coordinate.

**Verdict: PROOF** (analytic plus spot-check).

Reproducer: `tools/archaeology/fixedmul-proof.c`.

## 3. The random table — PROVEN not a standard PRNG

`rndtable[256]` (`m_random.c`) drives every damage roll, monster decision and
gunshot spread. Folklore says "random numbers someone typed in". What can be
shown is what it is **not**.

The entire 2^32 seed space of every ubiquitous generator of the era was
brute-forced, requiring an exact 256-byte match:

| generator | result |
|-----------|--------|
| ANSI C LCG (`1103515245·s+12345`, `>>16 & 0x7fff`), `%256` and `&255` | no match |
| Borland, Microsoft C, V7 LCG variants | no match |
| 4.3BSD `rand()` low byte (full 2^32) | no match |
| `drand48` top byte / `lrand48() % 256` (full 2^32) | no match |
| BSD `random()` additive feedback, both inits, warmup 0 and 310 | no match |

No seed of any canonical C PRNG produces DOOM's table. It was hand-authored, or
came from a source outside the standard libraries. The statistics fit that
story: mean **128.85**, not 127.5 (ea-007); only **166** of 256 values distinct
(ea-008); **90** of the 256 byte values never appear (ea-009). That is a worse
distribution than any LCG gives, the fingerprint of human typing rather than an
algorithm. It is an exhaustive negative result, not an absence of evidence.

Reproducer (the statistics): `tools/archaeology/rndtable-stats.c`, with the
extracted table in `tools/archaeology/rndtable.h`. The brute-force searches are
not in the tree; `git show 2a6a2de:tools/archaeology/prng-crack-full.c` (and
`prng-crack-lcg.c`, `prng-crack-bsd.c`) recovers them.

## 4. Gamma tables — approximate power curves, no exact recipe

`gammatable[5][256]` (`v_video.c`) is the display brightness correction. Each
level is fitted to `round(255 · ((i+0.5)/256) ^ (1/γ))` by a 0.001-step sweep
of γ; the residuals are the true minima:

| level | best γ | residual mismatches |
|-------|--------|---------------------|
| 0 | 1.006 | 5 / 256 (ea-010) |
| 1 | 1.150 | 34 (ea-011) |
| 2 | 1.341 | 36 (ea-012) |
| 3 | 1.609 | 41 (ea-013) |
| 4 | 2.011 | 34 (ea-014) |

The curves are unmistakably power functions, and the black floors are exact
powers of two: the darkest input maps to 1, 2, 4, 8, 16 for levels 0 to 4.
But **no single closed form reproduces any level exactly**, and level 0 is not
even the identity. Verdict: hand-adjusted power curves, or a generator tool
now lost. Unlike the trig tables these are display-only and never touch the
sim, so exactness is cosmetic; they are kept as canon data, not regenerated.

Reproducer: `tools/archaeology/gamma-crack.mjs`.

## 5. P_AproxDistance — BOUNDED-EMPIRICAL

`dist = max(|dx|,|dy|) + min(|dx|,|dy|)/2`, the octagonal "alpha max plus beta
min" norm (`p_maputl.c`). The sim uses it for monster melee and missile range
checks (`P_CheckMeleeRange`, `P_CheckMissileRange`), `P_LookForPlayers`,
missile and lost-soul travel time, floater height-seeking in `P_ZMovement`, and
`P_HitSlideLine`. `S_AdjustSoundParams` computes the same formula inline (§10).

Two analyses are needed, because the engine divides by 2 with `>>1` (a floor),
not real arithmetic. The floor penalty matters at small magnitudes and is
negligible at game-coordinate scales.

**Continuous analysis, proven by calculus.** Let t = min/max ∈ [0,1]:

```
r(t) = (1 + t/2) / sqrt(1+t²),   r'(t) = (½−t) / (1+t²)^{3/2}
```

r'(t) = 0 only at t = ½, the unique interior maximum on [0,1]. r(0) = 1 and
r(½) = sqrt(1.25), so the maximum error is **+11.8% at 26.6° (arctan ½)**
(ea-015), *not* at 45°, where it is only **+6.1%** (ea-016). On the axes the
error is **0.0%** (ea-017). The formula never underestimates, so a range check
never sees a target as closer than it is. Continuous supremum:
sqrt(1.25) − 1 ≈ +11.803%.

**Integer analysis, exhaustive.** `>>1` floors. At (dx,dy) = (1,1): max = 1,
min = 1, `1>>1 = 0`, so approx = 2 against an exact sqrt(2) ≈ 1.414, a ratio of
sqrt(2), **+41.4%** (ea-044). That is the integer supremum over all nonzero
int32 inputs: for min = 1, max = m the ratio is (m+1)/sqrt(m²+1), maximized at
m = 1, and an exhaustive check over all M ≤ 1000 confirms it. The floor penalty
decays like 1/max; at M = 65,536 a sweep of all 65,536 pairs keeps the integer
supremum within **11.81%** (ea-045). DOOM actors are tens to thousands of map
units apart, so the operative in-game bound is ≤ 11.81%. Quoting "+11.8%"
without the magnitude qualifier is false for tiny inputs.

It feeds the sim, so it is frozen.

Reproducer: `tools/archaeology/aprox-distance-crack.c`.

## 5a. R_PointToAngle / SlopeDiv — BOUNDED-EMPIRICAL

`R_PointToAngle` (`r_main.c`) maps (dx,dy) to an `angle_t` (uint32 binary
angle) through an 8-octant structure; each octant looks up
`tantoangle[SlopeDiv(min, max)]`.

**SlopeDiv range.** `SlopeDiv` (`tables.c`) has two branches:

- if `den < 512`, return `SLOPERANGE` (2048);
- otherwise `ans = (num<<3)/(den>>8)`, return `min(ans, SLOPERANGE)`.

Both return a value in [0, 2048] (ea-047 = 2048). It is called with
num ≤ den, both non-negative, so no path escapes the guard or the clamp. The
reproducer spot-checks the edges (num = 0, den < 512, huge num, num == den).

**Fine-angle round trip.** Proof by enumerating all 8,192 fine angles. For
each angle i, take the vector at the centre of its bin,
`(dx,dy) = K·(cos((i+0.5)·2π/8192), sin(...))`, run it through
`R_PointToAngle`, shift by `ANGLETOFINESHIFT` (19), and measure
|fine_got − i| in fine-angle steps (1 step = 360°/8192 ≈ 0.044°).

- *FRACUNIT scale* (K = 65,536): worst error **3 fine-angle steps** (0.13°)
  (ea-046). The `>>8` truncation in SlopeDiv quantizes the `tantoangle` index
  hardest when den ≈ FRACUNIT.
- *Game scale* (K = 16·FRACUNIT and up): worst error **1 step** (0.044°). No
  fine angle errs by more than one step.

DOOM objects are far more than one FRACUNIT apart, so the operative bound in
play is one fine-angle step. The near-axis octant term
(`ANG90 − 1 − tantoangle[...]`) accounts for the ±1 bin shift at octant seams.

*Residuals:* (0,0) returns 0 (degenerate, skipped). `abs(INT_MIN)` is UB, as
in §2.

**Verdict: BOUNDED-EMPIRICAL.** SlopeDiv's range is proven by construction; the
round trip by enumeration of every fine angle. It feeds the sim
(`R_PointToAngle2` sets monster facing, missile launch angles, damage thrust,
wall-slide direction and the player's death view), so it is frozen.

Reproducer: `tools/archaeology/angle-roundtrip-check.c`.

## 6. COLORMAP light-diminishing tables — CRACKED for id's palette, not universal

The 8,704-byte `COLORMAP` lump holds 34 maps of 256 bytes. Maps 0 to 31 are the
light levels that darken every wall, floor and sprite with distance; map 32 is
the invulnerability inverse; map 33 is all black. It is the most-consulted
table in the renderer, and it was built by a lost tool doing a nearest-colour
search over the palette.

**Light levels (maps 0 to 31).** The exact recipe for id's palette:

```
colormap[L][i] = argmin_j || palette[j] − round(palette[i] · (32−L)/32) ||²
```

Darken each palette colour by the linear factor `(32−L)/32`, round to nearest,
and take the **Euclidean**-nearest palette index. Against `doom.wad` this
reproduces COLORMAP **exactly: 0 of 8,192 entries differ, all 32 levels exact**
(ea-018). Nearby recipes are not close:

| variant | mismatches / 8,192 |
|---------|--------------------|
| the recipe (Euclidean, round, `(32−L)/32`) | 0 (ea-018) |
| truncate instead of round | 313 (ea-019) |
| `(31−L)/31` scale | 2,373 (ea-020) |
| Manhattan metric | 1,208 (ea-021) |
| luma-weighted metric | 1,400 |

Map 0 is not pure identity: 249 of 256 entries map to themselves (ea-022). The
DOOM palette contains near-duplicate entries, so a few colours have a nearer
neighbour than themselves.

**This is one palette, not several.** `doom2`, `plutonia`, `tnt` and `chex`
ship PLAYPAL and COLORMAP byte-identical to `doom.wad` (4 of 4, ea-049), so
running the recipe on them re-runs the same computation on the same input and
adds no evidence.

**The recipe's index matching is not universal.** `hacx.wad` has a genuinely
independent palette (748 of 768 palette bytes differ from DOOM's). The recipe
misses **3,517 of 8,192** entries of HACX's COLORMAP (43%, ea-048) and
reproduces **none** of its 32 levels, under every metric and scale variant
tried. HACX's COLORMAP is not junk: map 0 is 255/256 identity and map 31 is
255/256 near-black, in HACX's own palette.

**The darkening curve is universal.** Fitting the best scale per light level
against HACX's own colormap recovers the `(32−L)/32` curve independently, to
within 0.008 at every level:

| L | 0 | 4 | 8 | 12 | 16 | 20 | 24 | 28 |
|---|---|---|---|----|----|----|----|----|
| best fit | .994 | .878 | .750 | .624 | .496 | .375 | .249 | .124 |
| `(32−L)/32` | 1.000 | .875 | .750 | .625 | .500 | .375 | .250 | .125 |

So the curve is id's and it generalizes; the nearest-colour matching does not
(91 to 147 of 256 entries per mid-range level still miss at the best-fit
scale). Whatever built HACX's COLORMAP used the same curve and a different
matcher: tie-breaking, a restricted search range, or the dense near-duplicate
clusters in its palette. That part is an open question; the figures above are
the whole of what is established.

**Invulnerability map (32).** Every entry resolves to a grey-ramp colour by
inverse luma,

```
gray = 254 − ((76·r + 152·g + 34·b) >> 8)
```

then the nearest grey, matching **241 of 256** entries (ea-023; 15 mismatches,
ea-024). The residual 15 are nearest-colour tie-breaks in the grey ramp. The
weights sum to **262** (ea-025), a slope of about 1.023, not the textbook
0.299/0.587/0.114. That is why standard luma misses: the ITU BT.601 weights
rounded to 8-bit fixed point (**77/150/29**, sum 256) at the same `A = 254`
miss **91** entries (ea-026). The weight set has to be pinned for that figure
to mean anything, since nearby roundings score 88 to 93. Map 32 is a cosmetic
full-screen effect that never touches the sim, so it is kept as canon rather
than regenerated.

**Map 33:** all zeros, the blackout.

Reproducers: `tools/archaeology/colormap-crack.c` (maps 0 to 31),
`tools/archaeology/colormap-invuln-crack.c` (map 32),
`tools/archaeology/colormap-cross-palette.c` (the cross-WAD identity and HACX),
`tools/archaeology/wad-verify.mjs` (map-0 identity count).

### Method note

The recurring pattern: a "just how it's always been" blob is one of three
things.

- (a) A simple recipe plus a fossilized rounding or precision quirk: the trig
  tables, COLORMAP, very nearly the gamma curves.
- (b) Provably equivalent to a faster modern form: `FixedDiv`.
- (c) Genuinely irreducible human data: `rndtable`.

Knowing which is the difference between copying the game and understanding it.

## 7. The bare-metal principle (and where "compute > lookup" is false)

A tempting instinct: 1993 shipped lookup tables because CPUs were slow, so a
modern port should compute in real time instead. **For DOOM's tables this is
backwards.** A table load from L1 costs about 4 cycles; `sin`/`tan`/`atan` cost
20 to 100; `COLORMAP` is a 256-entry nearest-colour *search*. Every one of
these tables is more expensive to recompute per call than to load.

The policy that follows (spec.md's magic-data policy): the only sanctioned
table transform is **shipped-blob → boot-generation** (compute once at
startup, look up at runtime, as §1 does for trig). Runtime lookup → runtime
transcendental is forbidden, because it is measured slower.

The same "measure, don't assume" caution applies to the one place the port
does compute at runtime. §2 proves the integer `FixedDiv` equals the double
form bit for bit, but "integer must be faster" is also false on some hardware.
Isolated wasm `FixedDiv` throughput, 2×10^8 iterations, double path against
int64 path:

| CPU | double | int64 | int64 speed |
|-----|--------|-------|-------------|
| i9-12900K (x86, modern) | 419 ms | 403 ms | +4% |
| Cortex-A76 (ARM, Pi 5)  | 754 ms | 630 ms | **+20%** |
| AMD G-T56N (x86 Bobcat) | 12,304 ms | 13,054 ms | −6% |
| i5-8350U (x86 Kaby Lake) | 964 ms | 2,725 ms | **−65%** |

The measurements are recorded in `tools/golden/bench-baseline.json`
(`history.v1.primitiveMicrobench`).

Old x86 64-bit `idiv` is slow (about 40 to 95 cycles of latency) against
double `divsd` (about 14 to 20), while ARM's integer divide wins. There is no
universally fastest divide. It does not matter for gameplay: `FixedDiv` is a
tiny slice of a frame, and end-to-end frame rate moved by about 2% or less on
each device measured before and after (`history.v1.frameThroughput` in the
same file). So the choice was made on the universal axes instead: simpler,
smaller, integer-exact and better on ARM, hence int64.

## Tables kept as-is (deliberately)

- **`gammatable`**: no exact closed form (§4); 1.25 KB, display-only. Kept.
- **`rndtable`**: irreducible hand-authored data (§3). Kept.
- **`COLORMAP`**: the recipe for id's palette is known (§6), but the lump is
  WAD-owned and **PWAD-overridable** (coloured lighting, fog, other palettes).
  Regenerating it would break those WADs for no gain, since it is loaded, not
  computed. It stays loaded from the WAD.

## 8. zlight/scalelight constants: DISTMAP=2, LIGHTZSHIFT=20 — IRREDUCIBLE

renderer.md §2.3 documents the structure of these tables. This section is about
why the two constants have the values they do.

`R_InitLightTables` (`r_main.c`) builds `zlight`, and `R_ExecuteSetViewSize`
builds `scalelight`, from two constants:

```
DISTMAP     = 2         (r_main.c, just above R_InitLightTables)
LIGHTZSHIFT = 20        (r_main.h)
```

### What LIGHTZSHIFT=20 encodes

The zlight index `j` encodes distance as `(j+1) << LIGHTZSHIFT` in fixed
point. With LIGHTZSHIFT = 20 and FRACBITS = 16:

```
world distance (map units) = (j+1) · 2^(LIGHTZSHIFT − FRACBITS) = (j+1) · 16
```

So the `MAXLIGHTZ = 128` entries span **16 to 2048 map units** (ea-028),
roughly from inside one blockmap cell to the far end of most indoor corridors.
LIGHTZSHIFT = 19 would compress the range to 8 to 1024 units; 21 would stretch
it to 32 to 4096. 20 is calibrated to the scale of DOOM's maps.

### What DISTMAP controls, quantified

In `R_InitLightTables` the distance term is `scale/DISTMAP` with
`scale = 160/(j+1)` (integer):
`FixedDiv(160·FRACUNIT, (j+1)<<20) >> 12` = `160·2^16·2^16 / ((j+1)·2^20) / 2^12`
= `160/(j+1)`, where 160 is `SCREENWIDTH/2`. Then
`level = startmap − scale/DISTMAP`, clamped to [0, NUMCOLORMAPS−1 = 31], with
`startmap = (15 − i)·4` for light level i.

Colormap index at light level i = 8 (startmap 28; colormap 0 is full bright,
31 fully dark):

| j | distance | DISTMAP=1 | DISTMAP=2 (canon) | DISTMAP=3 |
|---|----------|-----------|-------------------|-----------|
| 1 | 32 units | 0 | 0 | 2 |
| 2 | 48 units | 0 | 2 | 11 |
| 3 | 64 units | 0 | 8 | 15 |
| 4 | 80 units | 0 | 12 | 18 |
| 7 | 128 units | 8 | 18 | 22 |
| 9 | 160 units | 12 | 20 | 23 |
| 15 | 256 units | 18 | 23 | 25 |
| 31 | 512 units | 23 | 26 | 27 |
| 127 | 2048 units | 27 | 28 | 28 |

The farthest fully bright distance with DISTMAP = 2: 320 units at i = 14,
160 at i = 13, 32 at i = 8, and only 16 units (j = 0) for i ≤ 4. DISTMAP = 1
doubles that boundary (640 units at i = 14); DISTMAP = 3 cuts it to about
two thirds (208 units).

**Verdict: IRREDUCIBLE.** The structure (`startmap − scale/DISTMAP`) is read
straight from the code. DISTMAP = 2 and LIGHTZSHIFT = 20 are aesthetic tuning:
id's taste for how fast a corridor darkens with distance. Neither follows from
geometry, the WAD format, the screen resolution or any other constraint.
Sim-critical: no (lighting tables are renderer-side).

Reproducer: `tools/archaeology/zlight-distmap.mjs` (exact integer arithmetic,
all three DISTMAP variants, all 16 light levels).

## 9. checkcoord[12][4] — EQUIVALENCE PROVEN

renderer.md §3.5 describes `R_CheckBBox`. This section shows the table it
uses is correct.

```c
int checkcoord[12][4] = {
    {3,0,2,1},  // boxpos=0:  above-left
    {3,0,2,0},  // boxpos=1:  above-center
    {3,1,2,0},  // boxpos=2:  above-right
    {0},        // boxpos=3:  unused
    {2,0,2,1},  // boxpos=4:  left-center
    {0,0,0,0},  // boxpos=5:  INSIDE (early return true, never reached)
    {3,1,3,0},  // boxpos=6:  right-center
    {0},        // boxpos=7:  unused
    {2,0,3,1},  // boxpos=8:  below-left
    {2,1,3,1},  // boxpos=9:  below-center
    {2,1,3,0}   // boxpos=10: below-right
};
```

(`r_bsp.c`, above `R_CheckBBox`.) Entry values index the bspcoord array:
`0 = BOXTOP (max_y)`, `1 = BOXBOTTOM (min_y)`, `2 = BOXLEFT (min_x)`,
`3 = BOXRIGHT (max_x)`. Entry `{a,b,c,d}` gives `x1 = bspcoord[a]`,
`y1 = bspcoord[b]`, `x2 = bspcoord[c]`, `y2 = bspcoord[d]`.

### Geometric derivation

The nine valid boxpos values combine `boxx` (0 = left of, 1 = inside x,
2 = right of) and `boxy` (0 = above, 1 = inside y, 2 = below) as
`(boxy<<2) + boxx`. For each region the table picks the two corners that
subtend the **widest angular span** from the viewpoint:

| boxpos | region | corner 1 (x1,y1) | corner 2 (x2,y2) | reason |
|--------|--------|------------------|------------------|--------|
| 0 | above-left | right,top | left,bottom | diagonal, widest span from upper left |
| 1 | above-center | right,top | left,top | top edge |
| 2 | above-right | right,bottom | left,top | diagonal, widest span from upper right |
| 4 | left-center | left,top | left,bottom | left face |
| 5 | inside | — | — | always visible (early return true) |
| 6 | right-center | right,bottom | right,top | right face |
| 8 | below-left | left,top | right,bottom | diagonal, widest span from lower left |
| 9 | below-center | left,bottom | right,bottom | bottom edge |
| 10 | below-right | left,bottom | right,top | diagonal, widest span from lower right |

### Brute-force verification

The reproducer enumerates every corner pair for several viewpoints in each of
the 9 regions, computes each pair's angular span, and asserts the table's pair
is the widest. All 9 cases pass (ea-027 = 9).

**Verdict: EQUIVALENCE.** The table is a lookup form of a well-defined
geometric rule (pick the two bounding-box corners with the widest angular
span); a small `if`-tree could compute it, and the table avoids the branches.
It is not hand-authored: anyone applying the same reasoning gets the same nine
entries. Sim-critical: no (BSP culling is renderer-side).

Reproducer: `tools/archaeology/checkcoord-verify.mjs`.

## 10. s_sound.c — distance attenuation and stereo constants — IRREDUCIBLE

The constants at the top of `s_sound.c`:

| constant | value | meaning |
|----------|-------|---------|
| `S_MAX_VOLUME` | 127 | maximum internal volume |
| `S_CLOSE_DIST` | 160 × 0x10000 | inside this distance, volume is always max (160 map units; the source notes it was originally 200) |
| `S_CLIPPING_DIST` | 1200 × 0x10000 | beyond this distance the sound is inaudible |
| `S_ATTENUATOR` | `(S_CLIPPING_DIST−S_CLOSE_DIST)>>16` = **1040** | denominator of the linear attenuation |
| `NORM_PITCH` | 128 | unmodified playback pitch |
| `NORM_SEP` | 128 | centre stereo pan (0 full left, 255 full right) |
| `NORM_PRIORITY` | 64 | default sound priority |
| `S_STEREO_SWING` | 96 × 0x10000 | stereo spread in fixed point |
| `S_IFRACVOL` | 30 | defined, never referenced |
| `S_PITCH_PERTURB` | 1 | defined, never referenced |

**Volume** (`S_AdjustSoundParams`):

```
dist = adx + ady − min(adx, ady)/2      // P_AproxDistance's formula, inline
if dist > S_CLIPPING_DIST (1200) and gamemap != 8:  return 0  (inaudible)
if dist < S_CLOSE_DIST (160):  vol = snd_SfxVolume            (full volume)
else:                          vol = snd_SfxVolume · (1200 − dist) / 1040
```

The curve is **linear** from full volume at 160 units to zero at 1200. On map 8
of any episode (`gamemap == 8`: the ExM8 boss maps, and MAP08 in DOOM II) sounds
are never clipped: the distance is clamped to 1200 and the volume floor is 15,
so distant sounds stay faintly audible.

**Stereo:**

```
sep = 128 − (FixedMul(S_STEREO_SWING, finesine[relative_angle]) >> FRACBITS)
    = 128 − 96 · sin(angle of source relative to the listener)
```

Range [32, 224]: never hard left or right, always a blend.

**Pitch variation** (`S_StartSoundAtVolume`):

| sounds | perturbation | generator |
|--------|-------------|-----------|
| chainsaw (`sfx_sawup` to `sfx_sawhit`) | `pitch += 8 − (M_Random()&15)`, ±8 | **M_Random** |
| all others except `sfx_itemup` and `sfx_tink` | `pitch += 16 − (M_Random()&31)`, ±16 | **M_Random** |

Both use `M_Random`, not `P_Random`: pitch variation is cosmetic and does not
consume the simulation RNG.

**Verdict: IRREDUCIBLE.** S_CLOSE_DIST = 160, S_CLIPPING_DIST = 1200 and
S_STEREO_SWING = 96 are aesthetic tuning. The source ties the close distance
to "movement clipping resolution (see BLOCKMAP handling)" and notes the
clipping distance "does not fit the large outdoor areas", so both were known
compromises; no formula connects them to geometry. `S_StartSound` is called
from inside the playsim but consumes only `M_Random`, and `S_UpdateSounds`
runs from the main loop outside `G_Ticker`. **Sim-critical: no.** Sound state
never feeds `P_Random` or actor positions.

## 11. p_lights.c — strobe/glow/flicker constants — IRREDUCIBLE, P_Random sim-critical

Constants in `p_spec.h`:

| constant | value | meaning |
|----------|-------|---------|
| `GLOWSPEED` | 8 | light units per tic for the smooth glow (`T_Glow`) |
| `STROBEBRIGHT` | 5 | tics in the bright phase of a strobe |
| `FASTDARK` | 15 | tics in the dark phase of a fast strobe (about 0.43 s at 35 Hz) |
| `SLOWDARK` | 35 | tics in the dark phase of a slow strobe (1.0 s) |

Literal constants in `p_lights.c`:

| location | value | meaning |
|----------|-------|---------|
| `P_SpawnLightFlash` `maxtime` | 64 | AND mask for the bright phase: `(P_Random()&64)+1` is 1 or 65 tics |
| `P_SpawnLightFlash` `mintime` | 7 | AND mask for the dark phase: `(P_Random()&7)+1` is 1 to 8 tics |
| `T_FireFlicker` count | 4 | tics between fire-flicker steps |
| `T_FireFlicker` step | `(P_Random()&3)*16` | dims by 0, 16, 32 or 48 light units |
| `P_SpawnStrobeFlash` start offset | `(P_Random()&7)+1` | 1 to 8 tic stagger when not in sync |

`maxtime` and `mintime` are masks, not bounds: 64 has a single bit set, so a
flashing light stays bright for either 1 or 65 tics.

### P_Random consumption — sim-critical

What matters for demo sync is how many `P_Random` calls happen and when, not
the values they return. These thinkers consume the game RNG:

| thinker | P_Random calls |
|---------|----------------|
| `T_FireFlicker` | 1 every 4 tics |
| `T_LightFlash` | 1 per phase change (bright → dark or dark → bright) |
| `P_SpawnLightFlash` | 1 at spawn (initial count) |
| `P_SpawnStrobeFlash` (`inSync` = 0) | 1 at spawn (start offset) |
| `T_StrobeFlash`, `T_Glow` | **none** |

So the fire-flicker period (4) and the flash masks (64, 7) are sim-critical:
changing them changes when the next call happens and desyncs every demo on a
map with those sectors. The flicker step size and the strobe start mask change
only light levels, not the call count.

`STROBEBRIGHT`, `FASTDARK`, `SLOWDARK` and `GLOWSPEED` drive thinkers that
never call `P_Random`. They change only sector light levels, which no movement,
AI or damage code reads (light levels feed only the renderer, other light
thinkers, and savegames). They are frozen because every frame and every save
shows them, not because of RNG order.

**Verdict: IRREDUCIBLE.** STROBEBRIGHT = 5 tics (about 143 ms), FASTDARK = 15
and SLOWDARK = 35 are aesthetic choices for the two strobe speeds; GLOWSPEED = 8
is the step that makes the glow smooth; the flash masks and flicker period have
no geometric or physical derivation. **Sim-critical: yes** for the
`P_Random` consumers (`T_FireFlicker`, `T_LightFlash`, `P_SpawnLightFlash`,
`P_SpawnStrobeFlash`).

## 12. f_wipe.c — melt-wipe RNG: M_Random, NOT sim-critical

The screen melt (`wipe_initMelt`) sets each column's start delay with
`M_Random`:

```c
y[0] = -(M_Random() % 16);          // first column: 0 to 15 tics of delay
for (i = 1; i < width; i++) {
    r = (M_Random() % 3) - 1;       // -1, 0, or +1
    y[i] = y[i-1] + r;
    if (y[i] > 0) y[i] = 0;
    else if (y[i] == -16) y[i] = -15;   // clamp: at most 15 tics of delay
}
```

**The generator is `M_Random`, not `P_Random`** (`f_wipe.c` includes
`m_random.h` and calls only `M_Random`), so the wipe does not consume the
simulation RNG. The wipe runs between gameplay states, outside `G_Ticker`'s
tic, and demo replay does not depend on its RNG state.

**Speed curve** (`wipe_doMelt`):

```c
dy = (y[i] < 16) ? y[i] + 1 : 8;
```

A column with a negative `y` counts its delay down by one per tic. Once it
starts (`y ≥ 0`) it moves by `y + 1` rows while `y < 16`, so its position runs
0, 1, 3, 7, 15, 31 (doubling plus one each tic), and then falls a constant
**8 rows per tic**. That fast start followed by a steady fall is the melt
look. The 16-row threshold and the 8-row terminal speed are aesthetic choices.
Columns are 2 pixels wide (the melt moves `short`s).

Before the loop both screens are transposed to column-major order
(`wipe_shittyColMajorXform`, id's name) so the column-stride copy is
cache-friendly.

**Verdict: IRREDUCIBLE (constants), M_Random confirmed.** Because the wipe uses
`M_Random`, its column stagger can differ between a live run and a demo replay
without desync: the demo replays gameplay tics, not cosmetic frames.
**Sim-critical: no.**

### 13.6 st_stuff.c — cheat byte sequences — DECLARATIVE

The cheat sequences in `st_stuff.c` are stored pre-scrambled with `SCRAMBLE`
(`m_cheat.h`), a self-inverse bit permutation:

```c
#define SCRAMBLE(a) \
((((a)&1)<<7) + (((a)&2)<<5) + ((a)&4) + (((a)&8)<<1) \
 + (((a)&16)>>1) + ((a)&32) + (((a)&64)>>5) + (((a)&128)>>7))
```

It swaps bits 0↔7, 1↔6 and 3↔4 and leaves bits 2 and 5 in place, so
`SCRAMBLE(SCRAMBLE(a)) == a`: to decode a stored byte, apply SCRAMBLE once.
The bytes `1` and `0` in the sequences are parameter and end sentinels read by
`cht_CheckCheat`, not scrambled characters.

**Decoded sequences:**

| variable | plaintext | effect |
|----------|-----------|--------|
| `cheat_god_seq` | **iddqd** | god mode toggle |
| `cheat_ammo_seq` | **idkfa** | all weapons, keys, full ammo |
| `cheat_ammonokey_seq` | **idfa** | all weapons and full ammo, no keys |
| `cheat_noclip_seq` | **idspispopd** | no-clip (DOOM 1) |
| `cheat_commercial_noclip_seq` | **idclip** | no-clip (DOOM II) |
| `cheat_choppers_seq` | **idchoppers** | chainsaw and invulnerability |
| `cheat_mypos_seq` | **idmypos** | show angle and (x,y) in hex |
| `cheat_mus_seq` | **idmus** + 2 digits | change music track |
| `cheat_clev_seq` | **idclev** + 2 digits | warp to episode/map |
| `cheat_powerup_seq[0]` | **idbeholdv** | `pw_invulnerability` |
| `cheat_powerup_seq[1]` | **idbeholds** | `pw_strength` (berserk) |
| `cheat_powerup_seq[2]` | **idbeholdi** | `pw_invisibility` |
| `cheat_powerup_seq[3]` | **idbeholdr** | `pw_ironfeet` (radiation suit) |
| `cheat_powerup_seq[4]` | **idbeholda** | `pw_allmap` (computer map) |
| `cheat_powerup_seq[5]` | **idbeholdl** | `pw_infrared` (light amplification) |
| `cheat_powerup_seq[6]` | **idbehold** | show the BEHOLD menu |

The shared "idbehold" prefix bytes `0xb2,0x26,0x62,0xa6,0x32,0xf6,0x36,0x26`
decode to `i,d,b,e,h,o,l,d`. `ST_Responder` loops `i = 0..5` over
`cheat_powerup[i]` and toggles `plyr->powers[i]` directly, which fixes the
index-to-power mapping above.

**Verdict: DECLARATIVE.** SCRAMBLE is trivial obfuscation, reversible in one
operation. Sim-critical: no (cheats are processed in `ST_Responder`, outside
