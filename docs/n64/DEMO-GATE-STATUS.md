# N64 demo sim-hash gate (task 20.4c) — status

**State: infrastructure built and verified; gate does NOT yet pass. 20.4c stays open.**

## What works
- `tools/n64/n64_hash.c` — per-tic state hash, **algorithm byte-identical** to
  `tools/freestanding/i_main.c` `fs_state_hash()` and `web_state_hash()` (same
  seed `0x9e3779b9 ^ gametic`, same FNV prime, same fields in the same order:
  prndindex, per-player mo x/y/angle + health, sector floor/ceiling heights,
  thinker count). Verified by direct source comparison.
- The frame loop in `n64_main.c` records one hash per unique `gametic` into
  `n64_trace[]` (10000-entry RDRAM buffer), extractable over the ares GDB stub
  with `dump binary memory`.
- `make N64_TIMEDEMO=demoN` builds a per-demo ROM; the sim runs and the trace
  fills (confirmed climbing 3 → 215 → … → 4026).
- `tools/n64/run-n64-demos.sh` — gate scaffold (build per IWAD/demo, run under
  ares, dump the trace, compare to `tools/golden/<iwad>-<demo>.json`).

## The blocker (root-caused, not a slow-capture issue)
The captured hashes do **not** match the golden — `golden[0]` (0x266402b3 for
doom-demo1) appears nowhere in the dumped trace. Cause:

1. The state hash includes `gametic` (`h = 0x9e3779b9 ^ gametic`).
2. The golden was generated by `callMain(['-timedemo','demoN'])` — timingdemo
   mode, where the demo plays immediately from a fixed `gametic` base and the
   run ends via `I_Error("timed N gametics")`.
3. On N64, `-timedemo` is passed in `myargv` but timingdemo mode does **not**
   engage: the trace grows past the demo length (4026 > doom-demo1's 1710), so
   the port is running the ordinary attract loop (title → demo1 → demo2 → …),
   not a single timed demo. `gametic` therefore includes title/menu tics and
   never aligns with the golden's `gametic` base — so the hashes differ from
   tic 0 even if the underlying simulation is correct.

## Next step to close 20.4c
Make `-timedemo` engage in the N64 port exactly as it does under wasm, so demo
playback starts at the same `gametic` base and terminates via the timing
`I_Error`. Investigate why `G_TimeDemo`/`timingdemo` is not set after
`D_DoomMain` on this target (arg parsing? the split-out D_DoomFrame demo path?).
Once one demo's trace matches the golden bit-identically, `run-n64-demos.sh`
fans out to the 4 IWADs. Only then does the DoD (13/13 bit-identical) hold.

Until then this is infrastructure, not a passing gate — do not wire it into the
main suite as green.
